# 论断—证据台账（Claim-Evidence Ledger）

## 为什么要有

提取表是**按文献**组织的：一篇论文一行。但正文是**按论断**组织的：一句话可能包含两个独立判断，需要两篇不同文献支撑。

没有台账，写作时只能“凭对文献的整体印象”发挥，于是出现三种错误：张冠李戴、把部分支持写成强支持、把有条件的结论写成普适结论。

台账把“文献里有什么”翻译成“哪句话可以被哪条证据支持”。

## 什么时候建

- **S4 精读时开始**：每读完一篇，把可支持的论断拆出来记入；
- **S5 写作前补齐**：按章节需要的论断反查台账，缺证据就回 S4/S3；
- **S6 审计时核**：逐条比对正文与台账。

## 字段

| 字段 | 说明 |
|---|---|
| `claim_id` | C001 递增 |
| `claim_text` | 一句可判断真假的论断，不写“效果很好” |
| `paper_id` | 候选表 ID（AM-0001） |
| `evidence_id` | E001 递增，指向具体证据 |
| `location` | 页码 / 章节 / 表号 |
| `evidence_type` | 实验 / 理论 / 案例 / 综述 / 数据集 |
| `support` | 强支持 / 部分支持 / 反对 / 无关 |
| `conditions` | 数据集、任务、模型、场景——**必填** |
| `verification` | 全文核验 / 摘要核验 / 元数据核验 / 未核验 |
| `note` | 待核、冲突、提醒 |

## 五条规则

1. **一个论断一行证据**：C001 有两篇支持就写两行，不合并。
2. **`support` 不许含糊**：只写四种取值；“部分支持”必须说明缺哪部分。
3. **`conditions` 必填**：没有条件的结论不能进正文。
4. **`verification` 分级使用**：
   - 全文核验：可支持方法、数字、局限等具体论断；
   - 摘要核验：只能支持摘要明确写出的内容；
   - 元数据核验：只能确认论文身份与出版信息；
   - 未核验：不能形成正式学术断言。
5. **反对证据必须进冲突地图**：`support=反对` 的行不是噪音，是第 5 章冲突分析的原料。

## 写作时怎么用

```text
先定 claim_text
  → 查台账有没有 evidence
    → 没有：回 S4 补读，或把句子降级为“待核”
    → 有：按 conditions 写限定，按 support 写强度
```

正文里的每个强论断（“X 能改善 Y”“A 优于 B”）都必须能指回一个 `claim_id`。背景性陈述可以引用综述或定义，不强制。

## S6 审计

1. 抽查 10 条强论断：正文句子、台账行、原文三处对得上；
2. 检查 `conditions` 是否被正文省略（省略即过度概括）；
3. 检查 `verification=摘要核验` 的行有没有被用来支持方法细节或实验数字；
4. 检查 `support=反对` 的行是否出现在冲突地图与正文。

## 与提取表的分工

| 表 | 回答的问题 |
|---|---|
| 提取表 | 这篇论文做了什么？ |
| 台账 | 哪句话能被哪条证据支持？ |

提取表的 `findings` 是原料，拆成 claim 后才可写作。
